# Model routing

Agents are mapped to **logical tiers** (`config/agent-registry.json`), and
tiers are mapped to **model aliases** (`config/model-routing.json`). No
agent hard-codes a model choice: the `model:` line in each `agents/*.md`
is generated by `node scripts/routing.mjs sync`, and
`node scripts/routing.mjs check` (in CI) fails if a file drifts from the
config.

## Default tiers

| Tier | Model | Fallbacks | Effort | Used by |
|---|---|---|---|---|
| reasoning | `opus` | sonnet | high | orchestrator, planner, architect, performance-engineer, improvement-analyst |
| coding | `sonnet` | opus | — | implementer, backend, database, test, refactoring, devops, integration, security-tester |
| fast | `haiku` | sonnet | — | project-discoverer, docs-writer |
| review | `opus` | sonnet | high | code-reviewer, architecture-reviewer, accessibility-auditor |
| security | `opus` | sonnet | high | security-reviewer, threat-modeler, dependency-auditor |
| ui | `sonnet` | opus | — | frontend-engineer, ui-director, visual-qa |

These are Claude Code **aliases** (`opus`, `sonnet`, `haiku`, `fable`,
`inherit`, or a full `claude-…` id). Claude Code resolves each alias to the
current model of that family available to the account. The allowlist lives
in `config/model-routing.json`, and the validator rejects anything else
(e.g. `gpt-4`).

The review and security tiers deliberately use a different model from the
coding tier. `checkRouting` reports an error if review and coding are
configured to the same model, so independent review differs in both
session and model.

## Resolution at dispatch time

```bash
node scripts/routing.mjs resolve <agent> --task TASK-007 --json
# {"agent":"backend-engineer","tier":"coding","model":"sonnet","fallbacks":["opus"],
#  "effort":null,"source":"registry","escalated":false,
#  "subagent_type":"project-kickstarter:backend-engineer","enabled":true}
```

The orchestrator passes `model` as the Agent tool's per-call `model`
parameter, which takes precedence over agent frontmatter. Precedence is:

1. the task's `model_tier`;
2. the project override `routing.agents.<agent>` in
   `.claude/agent-framework.json`;
3. the registry tier;
4. the specialist tier, for project specialists.

Then:

- **Fallbacks:** `--unavailable opus` (or an org that restricts
  `availableModels`) moves to the next fallback.
- **Escalation:** once `attempts` reaches `escalate_after_attempts`
  (default 2), the strongest available candidate is chosen, so later fix
  rounds run on a stronger model.

## Project overrides

```json
{
  "routing": {
    "tiers": { "coding": { "model": "opus", "fallbacks": ["sonnet"] } },
    "agents": { "docs-writer": "coding" },
    "escalate_after_attempts": 1
  }
}
```

Overrides are validated by `bootstrap.mjs validate`. Note that
`.claude/agent-framework.json` is protected: editing it asks for approval.

## What is not verified

There are no live runs (by user decision), so it is unverified whether
every alias is available to a given account, and how the runtime reacts to
an unavailable model. Fallback is triggered explicitly by the
orchestrator; it is not assumed to happen automatically.
